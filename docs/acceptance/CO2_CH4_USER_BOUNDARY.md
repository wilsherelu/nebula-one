# 同一 LCA 模型的 CO₂／CH₄ 核算边界验收

2026-10-13，在现有共享栈 One `18938`、LCA API `18931` 上，通过真实 HTTP、真引擎求解和持久化快照读回完成。本例使用人工输入的排放量，验证核算机制，不代表实测工厂数据，也不是 CBAM 合规结论。

## 模型与因子

一个归一化过程，参考产出 1 kg 产品，排放 10 kg 化石 CO₂ 和 0.1 kg 化石 CH₄。底层模型由 Nebula LCA provider 接口求解，One 绑定同一精确模型 revision，只调整交换层的用户核算规则。此例是通过公开 inline 模型合同送入引擎的测试模型，未改钢铁种子或用户原有模型。

两条气体流经引擎正式目录接口解析，namespace 为 `tiangong_open_data`、版本均为 `03.00.004`、单位 kg、环境区室为 `Emissions to air, unspecified`：

| 气体 | 精确 flow UUID | 本次运行 EF 3.1 气候因子 | 贡献 |
| --- | --- | ---: | ---: |
| 化石 CO₂ | `08a91e70-3ddc-11dd-923d-0050c2490048` | 1.0 | 10.00 kg CO₂-Eq |
| 化石 CH₄ | `08a91e70-3ddc-11dd-9610-0050c2490048` | 29.8 | 2.98 kg CO₂-Eq |

因子由运行库的 `indicator_contribution_receipts` 提供，脚本核对 `amount × cf_value` 与路径贡献一致，同时要求非零因子状态、因子哈希和 runtime 资产哈希。没有在 One 中写入因子或人为制造结果。29.8 是本次精确流／指标／runtime 的读回值，不是所有甲烷流的通用常数。

EF 指标：`climate change|climate change - radiative forcing as global warming potential (gwp100)`。本次 runtime 资产哈希为 `5b1562d26c385506cb03179050b53496f5c4054e278a0166878fc019c1b4563e`，LCA provider 提交为 `e3385d3fd040425a597ecf97607f4935ff04606c`。

## 三种用户规则的数值结果

| 规则 | 用户边界内计入量 | 边界外单列量 | 底层完整模型 LCA 总量 |
| --- | ---: | ---: | ---: |
| CO₂、CH₄ 全纳入 | 12.98 | 0.00 | 12.98 |
| 纳入 CO₂，排除 CH₄ | 10.00 | 2.98 | 12.98 |
| 排除 CO₂，纳入 CH₄ | 2.98 | 10.00 | 12.98 |

单位均为本次 1 kg 产品需求对应的 kg CO₂-Eq。每条规则绑定 `unit-process::co2` 或 `unit-process::ch4`，不是按过程名称匹配。每次方法单独校验并携带精确方法 ID、版本、哈希求解。

全纳入与 CO₂-only 的差值恰为 CH₄ 贡献 2.98；全纳入与 CH₄-only 的差值恰为 CO₂ 贡献 10.00。计入与排除对账，归集状态为 `executed_full`，没有未归属贡献或覆盖缺口。三次排放清单完全一致，使用同一模型 revision；结果保存为不同快照，重新 GET 后的内容哈希及方法身份一致。无用户方法的基线总量仍为 12.98。

把需求改为 2 kg 后，CO₂ 与 CH₄ 的加权贡献分别变为 20.00、5.96，批次总量 25.96，只缩放一次；除以 2 kg 后仍为 12.98 kg CO₂-Eq/kg 产品。批次总量与单位产品强度明确区分。

这里证明用户可调整核算纳入／排除与贡献归集规则。用户规则不会改变物理清单或基础特征化算法，缩小的核算边界也不被标成完整 PCF。任意数学公式编辑、任意因子编辑不属于这次已验收能力。
